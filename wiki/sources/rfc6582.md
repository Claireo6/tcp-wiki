# The NewReno Modification to TCP's Fast Recovery Algorithm

Obsoletes: 3782
Updates: None

> first implemented in the 1990 BSD Reno release, and referred to as the "Reno algorithm" in [FF96] [RFC 6582 §1]

## 要解決的問題
Reno 在同一個視窗遺失多個封包時有兩個問題：常常會逾時；即使沒有逾時，也可能發生多次 fast retransmit 與多次視窗縮減 [RFC 6582 §1]。

> Two problems arise with Reno TCP when multiple packet losses occur in a single window. [RFC 6582 §1]

## 核心概念
- **Partial acknowledgment**：多個封包遺失時，重傳區段換來的 ACK 只會確認「進入 fast retransmit 前已送出資料」的一部分 [RFC 6582 §1]。
- **`recover` 變數**：記錄 fast recovery 結束前必須被確認的送出序號 [RFC 6582 §2]。
- 這種對 partial ACK 的處理方式最早由 Janey Hoe 提出 [RFC 6582 §1]。

> However, if there are multiple packet drops, then the acknowledgment for the retransmitted packet will acknowledge some but not all of the packets transmitted before the fast retransmit. We call this acknowledgment a partial acknowledgment. [RFC 6582 §1]

## 適用範圍
本文件適用於無法使用 SACK 選項的 TCP 連線 [RFC 6582 §1]；若 SACK 可用，作者認為 SACK 是處理多個遺失的最佳選擇 [RFC 6582 §3.2]。

## 演算法摘要
詳見 [NewReno 演算法頁](../algorithms/new-reno.md)。重點是：收到 partial ACK 時立即重傳下一個未確認的區段，並**留在** fast recovery，直到 ACK 確認到 `recover` 為止 [RFC 6582 §3.2]。

## 結論
沒有 SACK 的連線，重點是實作 NewReno 而不是 Reno；實作哪一種 NewReno 變體相對不重要 [RFC 6582 §8]。

> That is, the important thing is to implement NewReno instead of Reno for a TCP connection without SACK; it is less important exactly which variant of NewReno is implemented. [RFC 6582 §8]
